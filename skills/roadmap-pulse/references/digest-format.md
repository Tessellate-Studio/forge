# WEEKLY_DIGEST.md format (Step 5)

The digest is the persistent history of weekly priority decisions. Each run appends a dated section. Over months, this file becomes:

- A retrospective tool (what did I think was important in week N? what shifted by week N+8?).
- A training corpus for rubric-sdk (Track B) — the scores roadmap-pulse assigned + the actual completion outcomes feed back into the SDK's calibration.
- A fast read for "what's this week" — the user opens the latest section and sees the top 5-10 without re-running the skill.

## File location

`<repo-root>/WEEKLY_DIGEST.md`

If the file doesn't exist when roadmap-pulse runs the first time, create it with the header below.

## First-time header

```markdown
# Weekly digest — roadmap pulse history

This file is the append-only history of weekly priority decisions
generated by the `roadmap-pulse` skill. Each section below is one
weekly run, ordered newest-first (newest at the top).

Don't edit historical sections — they're a record of what was true
at that point in time. To update priorities, run roadmap-pulse again;
the latest section reflects the current state.

Maintained by: `.claude/skills/roadmap-pulse/`. Schedule: weekly,
default Sunday 16:00 IST.

---
```

## Per-run section format

Each run prepends (NOT appends — newest stays at the top) a section like this:

```markdown

| 2 | Reddit launch posts | 60 | 79.2 (×1.2 goal ×1.1 unblock) | Must | Highest-priority acquisition channel for closed beta. Awaits #1. |
| 3 | … | … | … | … | … |
```

## Diff section ("What changed since last week")

This is the most valuable section for retrospectives. To build it, read the prior week's section in `WEEKLY_DIGEST.md`:

1. Compute the set difference between this week's top-10 and last week's top-10.
2. For tasks present in both: compute the score delta + band shift.
3. For tasks new to top-10: compute their previous rank if known (otherwise mark "new entry").
4. For tasks dropped from top-10: compute where they went (still open, lower-ranked? shipped? deferred?).
5. Record dependency persistences from Step 3 and honesty-pass cleanups from Step 1.

If `WEEKLY_DIGEST.md` is new (first run), skip the diff section entirely with a `*(First run — no comparison available.)*` placeholder.

## Run metadata section

This is the audit trail for the run. Keep it short — readers care about priorities, not the skill's plumbing — but enough that a future debugging session can reconstruct what happened:

- The goals input (so a future reader knows what context drove the prioritization).
- The total count of open tasks scored (sanity-check against the BACKLOG).
- The selection cutoff (what score made it into top-10).
- The rubric-sdk version (so the digest stays reproducible even if the SDK evolves).
- The next scheduled run (so the user knows the cadence is healthy).

## Don't bloat the digest

Each section should fit on one screen. If the prioritized list is 30 tasks, only the top 10 go in the digest — the rest can stay in the BACKLOG. Same for the "what changed" section — top 5 changes, not every score delta.

The digest is a curated story of the week's priorities. Not a database dump.
